한국어와 영어가 섞인 노트에서 에이전트 메모리 도구가 정답 노트를 얼마나 찾는지 Hit@5[^hit5](100개 중)로 쟀습니다. 정답 노트가 상위 5개 안에 든 질문의 수입니다. 에이전트 검색[^agent]은 질문 100개 중 99개에서 적중했고, BM25[^bm25] 검색만 쓰는 베이스라인[^baseline]은 84였습니다. 권장 구성대로 끝까지 돌렸고 질문할 때 언어 모델을 부르지 않는 제품 가운데는 ir이 93으로 가장 높았고, 이때 선택 사항인 리랭킹[^rerank] 단계는 꺼 둔 상태였습니다. 우리가 쓰던 의미 검색 설정은 48이었습니다. 이 설정은 임베딩[^embedding]으로 뜻이 가까운 노트를 찾는 방식입니다. 표에는 점수가 끝까지 나온 행마다 p값[^p]을 함께 적었고, 검정은 부호 검정[^sign]입니다.

한국어와 영어가 섞인 실제 노트로 에이전트 메모리 도구를 견준 현장 시험입니다. 새 메모리 시스템을 만든 것이 아니라, 직접 잰 비교와 그 결과로 고른 구성을 보여 줍니다. 잰 구성은 79개이고 노트 287개와 질문 100개에 같은 방식을 썼습니다. 이 저장소의 표는 그 가운데 29행을 싣고, 26개는 권장 구성대로 끝까지 돌아 실행 점검을 통과했습니다. 나머지 3행은 예외입니다. 중간 결과만 있어 보류 중인 Hindsight, 우리가 쓰던 의미 검색 설정을 보여 주는 참고 행 하나, BM25 베이스라인입니다.

### 결론

이 결론은 한국어와 영어가 섞인 노트에서 잰 에이전트 메모리 도구에 대한 것이며, 모두 위 표에 근거합니다.

- <!-- claim:C1 -->에이전트 검색을 BM25 검색 위에 얹으면 Hit@5가 100개 중 99였고(베이스라인은 84), 16승 1패에 p값이 0.001보다 작으며, answer score는 189 대 150이고 같은 설정을 다시 돌린 값은 98-99였습니다.
- <!-- claim:C2 -->표에 있는 기억 저장 제품은 모두 권장 구성대로 끝까지 돌렸는데, BM25 베이스라인을 넘는다고 확인된 것은 없었습니다. 5개 중 가장 높은 MemPalace(83)도 4승 5패에 p값이 1.000이었고, 나머지는 66-82였습니다. Hindsight는 보류 중이라 이 결론에 넣지 않았습니다.
- <!-- claim:C3 -->표에 있는 임베딩 중심 도구 5개(모두 권장 구성대로 끝까지 돌림)는 46-81로 베이스라인을 넘지 못했고 임베딩을 바꾸고 최소 유사도를 낮춘 Basic Memory 권장 구성이 46으로 가장 낮았지만, BM25와 벡터를 섞는 ir은 93으로 베이스라인보다 높았습니다(10승 1패, p값 0.012).
- <!-- claim:C4 -->권장 구성대로 끝까지 돌렸고 질문할 때 언어 모델을 부르지 않는 제품 가운데 ir이 93으로 가장 높았고, answer score는 167이며, 10승 1패에 p값이 0.012였습니다.
- <!-- claim:C5 -->KURE-v2 리랭킹을 BM25 검색 상위 50개에 붙이면 Hit@5가 88이 되었고, answer score는 확인되게 올랐습니다(10승 0패, p값 0.002). Hit@5의 차이는 아직 확인되지 않았습니다(4승 0패, p값 0.125).
- <!-- claim:C6 -->계층 색인은 91이고 멀티홉[^multihop] 질문 25개 중 정답 노트 둘 다 상위 5개 안에 든 수가 5에서 22로 늘지만(17승 0패), 지식 갱신 질문[^update] 30개에서는 Hit@5가 28에서 24-25로 줄었습니다.
- <!-- claim:C7 -->상위권은 만점 가까이 몰려(천장 효과) 이 질문 100개로는 상위권 사이의 차이를 가리기 어렵고, 권장 구성대로 끝까지 돌려 유효로 판정된 구성 가운데 표에서 98 이상은 에이전트 검색 하나(99)입니다. 표에서 뺀 구성 가운데 노트 파일을 직접 읽는 에이전트 둘은 99와 100이지만 같은 조건으로 견줄 수 없습니다([results/excluded.ko.md](results/excluded.ko.md)).
- <!-- claim:C8 -->79개 구성을 같은 질문 100개로 쟀고 표에는 29개를 싣습니다. 나머지 83개는 별도 문서([results/excluded.ko.md](results/excluded.ko.md))에 있고, 이 가운데 50개는 잰 뒤에 뺐고 13개는 돌리지 않고 결과를 예상해 닫았으며 20개는 잴 수 없었습니다.

### 표와 수치에 대하여

표는 한 원본 `results/results.csv`에서 만듭니다. 위 표의 한 행에는 번호, 이름, 종류, Hit@5, 베이스라인 대비 승과 패, p값, 짧은 비고가 있습니다. 여기에 분류, 설치 조건, 권장 구성대로 돌았는가, 권장 구성과 다른 점을 더한 13개 칸의 전체 표는 `results/full-table.ko.md`에 있습니다. 행은 Hit@5가 높은 순서로 놓고, Hit@5가 같으면 answer score가 높은 쪽을, 그다음에는 식별자 순서를 따릅니다. 같은 Hit@5는 `#` 열에서 같은 번호를 씁니다. Hindsight 행에는 중간 결과인 값 둘을 실행 순서(첫 실행, 둘째 실행)대로 적고, 실행마다의 조건을 함께 적었습니다. 이 행의 `#`, 승, 패, p값 칸이 빈 것은 끝내지 못한 실행의 중간 값을 베이스라인과 견주지 않기 때문입니다. Hindsight 행은 보류 중이라 # 번호가 없고, 표 안 자리는 둘째 실행 값(86)을 따르며, 두 중간 값은 실행 순서대로 적습니다.

전체 표에서 '권장 구성대로 돌았는가' 칸의 '예'는 도구 설명서가 권하는 설정대로 돌았고 바꾼 점은 비고 칸에 적었다는 뜻입니다. 기법은 우리가 만든 구성이거나 도구 조합이라 도구의 권장 구성이 따로 없으므로, '예'는 설명서에 적힌 가장 단순한 설정으로 돌렸다는 뜻입니다. 베이스라인과 참고 행은 해당 없음입니다.

위 결론의 수치 대부분은 위 표나 전체 표에서 읽거나 다시 셀 수 있습니다. 행마다 Hit@5, 승, 패, p값, 멀티홉 칸, answer score가 그렇습니다. 세 가지는 표 밖에서 옵니다. 반복 실행 값(에이전트 검색 98-99, 계층 색인 90-92, 지식 갱신 질문의 24-25)은 반복 실행 기록에서 옵니다. 질문 종류별 짝 비교 수(멀티홉 질문의 17승 0패, 지식 갱신 질문의 28에서 24-25)는 베이스라인과 같은 질문끼리 비교한 결과에서 옵니다. KURE-v2 리랭킹의 answer score 비교(10승 0패, 0.002)는 같은 비교를 answer score에 적용한 값입니다. 이 값들은 두 표 어느 쪽의 칸도 아닙니다.

### 노트 다시 쓰기 점검

세 번째 연구 질문의 답입니다. 노트 64개를 4가지 방법으로 다시 쓰게 한 256쌍을 원문과 하나씩 대조했습니다. 원문에 없는 사실이 들어가거나 "추정", "미검증" 같은 단서가 떨어져 단정이 된 쌍이 55쌍(21%)이었습니다. 지금 규칙으로 실제로 바뀐 노트 48개 가운데는 12개(25%)가 지적됐습니다. 대조를 맡은 두 문맥이 같은 20쌍을 따로 보고 16쌍에서 판정이 같았으며(kappa 0.38) 일치가 낮으므로, 비율의 크기는 어림으로 읽어야 합니다. 운영에서 얻은 교훈은 다시 쓴 노트를 올리기 전에 원문 대조 관문을 두는 것입니다. 노트 원본과 다시 쓴 판은 싣지 않고 수치와 방법만 싣습니다.

## 연구 질문

이 시험은 3가지를 묻습니다.

1. 기억 저장 제품이나 검색 도구가, 한국어와 영어가 섞인 노트에서 BM25 베이스라인보다 정답 노트를 더 잘 찾는가.
2. 어떤 구성, 곧 도구와 설정이 가장 잘 찾고, 그 값은 질문당 모델 호출 수와 준비 시간으로 얼마가 드는가.
3. 모델이 노트를 다시 쓸 때 원문의 사실이 지켜지는가.

비교한 방식에는 BM25 검색, 임베딩 검색, 모델로 기억할 내용을 뽑거나 요약해 저장하는 기억 저장소, 에이전트 검색, 리랭킹을 더한 구성이 들어 있습니다. 적중은 정답 노트가 돌려준 상위 5개 안에 든다는 뜻입니다(Hit@5).

## 자료와 표본

표본은 노트 287개입니다. 개인 지식 저장소의 작업 노트 193개와 소식지 94판으로 이루어져 있고, 한 폴더에 평면으로 둔 마크다운 파일이며 맨 앞에 YAML 머리말이 있습니다. 개인정보가 든 노트와 운영 기록은 표본에서 뺐습니다. 노트에는 한국어와 영어가 섞여 있고, 언어별 비율은 재지 않았습니다.

질문은 100개이고 표본 노트에서 만들었습니다.

| 질문 종류 | 개수 | 무엇을 보는가 |
|---|---|---|
| 바로 묻는 질문 | 20 | 질문이 노트의 낱말을 그대로 씁니다 |
| 다르게 표현한 질문 | 25 | 같은 뜻을 다른 낱말로 묻습니다 |
| 멀티홉 질문 | 25 | 노트 두 개를 함께 읽어야 답할 수 있습니다 |
| 지식 갱신 질문 | 30 | 나중 노트에서 바뀐 값을 묻습니다 |

표본 노트와 질문 원문은 공개하지 않습니다. 대신 공개 자료로 만든 시연 표본(노트 12개와 질문 10개)이 `demo/`에 있어서, 같은 도구로 끝까지 돌려 볼 수 있습니다.

### 자료 형식

질문 파일은 한 줄에 질문 하나인 JSON Lines입니다. `q`는 질문 번호, `type`은 질문 종류, `question`은 질문 글, `gold_files`는 정답 노트 파일 이름 목록입니다. 자세한 규칙은 `spec/question-format.md`에 있습니다. 도구가 돌려준 상위 5개는 한 줄에 하나씩 `{"config", "q", "top"}` 꼴로 `top5.jsonl`에 적습니다. 결과표의 유일한 원본은 `results/results.csv`이고, 이 문서의 표는 `tools/make_tables.py`가 그 파일에서 만듭니다.

## 비교 도구 고른 법

시험 후보 84개는 긴 목록 1,119행을 거르고 점수를 매겨 올렸습니다. 이 가운데 12개는 규칙으로 뽑았고, 72개는 도구와 논문을 더 넓게 살펴 요청에 따라 손으로 더했습니다. 우리 쪽 구성 3개와 조합 2개를 포함해, 끝까지 잰 구성은 79개입니다.

도구마다 그 도구 설명서가 권하는 설정으로 돌렸습니다. 도구 가운데는 기본 모델이 우리 모델 사용 규칙(쓰지 않는 모델을 정해 둔 규칙)에 걸리는 것이 있고, 그런 경우에는 다른 모델로 바꾸고 바꾼 내용을 전체 표의 비고 칸에 적었습니다. 권장 구성 실행마다 따로 실행 점검을 해서 유효, 일부만 유효, 무효로 나눴습니다. 표에는 유효로 판정된 26개와 세 가지 예외만 싣습니다.

- 베이스라인: 모든 비교의 기준이라 싣습니다.
- 참고 행: 우리가 쓰던 의미 검색 설정입니다. 유효이지만 어느 도구의 권장 구성도 아니라서 참고 행으로 따로 표시합니다.
- Hindsight: 보류 중입니다. 모델이 사실을 뽑고 기억을 묶어 정리하는 권장 구성이 필요로 하는 자원 때문에 끝까지 돌리지 못했습니다. 노트 287개에서 정리 단계 65%까지 가는 데 모델 호출이 약 2,000회 들었습니다. 실행마다의 조건을 한 행에 적고 값 둘을 중간 결과로 표시해 함께 싣습니다. 승, 패, p값 칸은 비워 둡니다.

그 밖의 구성은 이름과 점수(잰 것만)를 별도 문서 [results/excluded.ko.md](results/excluded.ko.md)에 싣습니다. 잰 79개 가운데 29개가 표에 있고, 표에 싣지 않은 구성은 83개입니다. 이 83개는 잰 뒤에 뺀 50개, 돌리지 않고 결과를 예상해 닫은 13개, 잴 수 없었던 20개입니다. 그 문서의 점수는 이 표의 점수와 같은 조건으로 견줄 수 없습니다.

84, 79, 13, 20은 세는 대상이 달라서 합이 하나로 맞지 않습니다. 84는 시험 후보로 올린 수입니다. 79는 잰 구성의 수이고, 우리 쪽 구성 3개와 조합 2개를 포함하며, 도구 하나가 구성 여러 개로 나올 수 있고, 예를 들어 권장 구성이 막힌 도구를 키 없는 구성으로 잰 경우가 있습니다. 예상해 닫은 13개는 단일 도구 7개와 조합 6개입니다. 잴 수 없었던 20개는 우리 모델 사용 규칙에 기본 모델이 걸리고 대체 모델로도 시험하지 못한 2개, 결정 기록과 세션 기록 도구처럼 이 질문으로 잴 수 없는 종류인 15개, 필요한 키를 주지 않은 3개입니다. 모두 구성 단위로 센 값이고, 84개와 하나씩 맞춰 보지는 않았습니다. 싣지 않은 83개와 잰 79개가 겹치는 것은 잰 뒤에 뺀 50개뿐이고, 돌리지 않고 닫은 13개와 잴 수 없었던 20개는 재지 않았습니다.

## 측정 절차와 지표

1. 구성마다 표본 노트 287개를 도구에 넣습니다. 설정은 위에서 말한 권장 구성입니다.
2. 질문 100개를 하나씩 던져 상위 5개 노트 파일 이름을 받습니다. 대부분 구성은 1번만 돌렸습니다.
3. 상위 5개 노트를 답을 쓰는 고정 단계에 줍니다. 모든 구성이 같은 모델, 같은 지시문을 쓰고, 노트마다 앞 6,000자만 읽습니다. 답을 쓰는 모델의 이름은 공개 자료에 적혀 있지 않습니다.
4. 베이스라인과 같은 질문끼리 짝지어 센 값을 `harness/pair_stats.py`로 냅니다.

### 지표 풀이

- Hit@5(100개 중): 정답 노트가 하나라도 상위 5개 안에 든 질문의 수입니다.
- 승과 패(베이스라인 대비): 같은 질문에서 베이스라인은 놓쳤는데 이 구성은 적중한 수가 승, 베이스라인은 적중했는데 이 구성은 놓친 수가 패입니다.
- p값: 두 구성이 실제로는 같은데 우연히 이만큼 갈릴 확률이며, 정확 양측 부호 검정으로 셉니다. 0.05보다 작으면 차이가 확인된 것으로 읽습니다.
- 멀티홉 질문 25개 중 정답 노트 둘 다 상위 5개 안에 든 수: 필요한 노트 두 개가 모두 상위 5개 안에 든 질문의 수입니다.
- answer score(답 점수, 200점 만점): 찾은 노트를 읽고 쓴 답을 질문마다 0점, 1점, 2점으로 채점해 100개를 더한 값입니다.
- 비용: 질문당 모델 호출 수, 노트를 넣는 데 걸린 시간, RAM입니다. 구성마다 세는 방식이 달라 대략값으로 읽어야 합니다.

## 채점과 채점자 일치

answer score는 어느 구성이 쓴 답인지 모르는 채점자가 매깁니다. 채점자는 질문과 질문 종류, 기준 답, 필요한 사실 목록, 답 하나만 봅니다. 답마다 기준 답만을 잣대로 0점, 1점, 2점을 매기고, 바깥 지식으로 사실을 인정하지 않으며, 짧은 답을 깎지 않습니다. 지식 갱신 질문과 멀티홉 질문의 규칙, 숫자와 날짜를 맞추는 규칙을 포함한 전체 기준은 `spec/rubric.md`에 있고, 답과 구성을 가리는 도구는 `harness/blind_grade.py`입니다.

채점자 일치는 이렇게 확인했습니다. 작업자도 첫 채점자도 아닌 문맥이 어느 구성의 답인지 가린 답 60개를 고정한 무작위 씨앗값(92053)으로 뽑아 다시 채점했습니다. 60개 가운데 59개는 두 채점자의 점수가 같았고 1개는 달랐습니다(2점과 1점). 일치 값은 0.983입니다. 이 값은 점수가 같은 비율이지 kappa가 아니며, 다시 채점한 것은 60개뿐입니다. 노트 다시 쓰기 점검은 따로 봐야 합니다. 거기서는 두 대조 문맥의 일치가 훨씬 낮았습니다(kappa 0.38, 결과 절의 마지막 부분).

## 통계

승과 패의 수로 하는 정확 양측 부호 검정은 구성마다 베이스라인과 같은 질문끼리 짝지어 합니다. 둘 다 적중했거나 둘 다 놓친 질문은 세지 않으며, p값이 0.05보다 작으면 확인된 차이로 부릅니다.

보정하지 않으면 우연만으로도 약 4개는 0.05보다 작게 나오는데, 비교가 78번이기 때문입니다(잰 구성 79개에서 베이스라인 자신을 뺀 수). 그래서 p값 하나만으로 결론을 내지 않고, 승과 패의 수를 함께 보십시오. 같은 설정을 반복해 돌린 구성은 반복 값의 범위를 같이 적습니다.

## 타당성 위협과 한계

- 표본은 노트 287개를 한 폴더에 둔 것이고, 실제 저장소는 약 1,800개에 폴더 구조가 있습니다. 실제 규모에서는 재지 않았습니다(미검증).
- 개인정보가 든 노트와 운영 기록을 표본에서 뺐으므로 그런 노트를 찾는 질문은 재지 않았습니다.
- 질문 100개를 표본 노트에서 만들어서 노트의 낱말이 질문에 묻었을 수 있고, BM25 검색에 유리했을 수 있습니다(추정).
- 상위권은 만점 가까이 몰려 있습니다(천장 효과). 표에 있는 행, 곧 권장 구성대로 끝까지 돌려 실행 점검에서 유효로 판정된 구성 가운데 98 이상은 에이전트 검색 하나(99)라서, 이 질문으로는 상위권 사이의 차이를 가리기 어렵습니다.
- 대부분 구성은 한 번만 돌렸습니다. 에이전트 검색은 같은 설정으로 다시 돌려도 상위 5개 목록이 36-45%의 질문에서 바뀌었고, Hit@5는 한 번은 98, 다른 한 번은 99였습니다. 계층 색인은 세 번이 90-92였습니다.
- answer score는 답을 쓰는 고정 단계가 노트마다 앞 6,000자만 읽은 값입니다. 찾는 일과 읽는 일을 함께 잰 값입니다.
- 78번 비교를 보정하지 않았습니다(통계 절).
- 노트 다시 쓰기 점검에서 대조 문맥의 일치가 낮았습니다(kappa 0.38). 비율의 크기는 어림으로 읽으십시오.
- 모델을 바꿔 돌린 구성은 제품 기본 설정 그대로의 점수가 아닙니다. 도구 버전은 2026-11 기준이고 이후 바뀔 수 있습니다.
- 표에는 끝까지 돌고 점검을 통과한 26개와 베이스라인, 참고 행 하나, 보류 중인 Hindsight만 있어서, 이 표로 "제품 일반"을 말할 수 없습니다.
- Hindsight의 두 값은 중간 결과입니다. 권장 구성을 끝까지 돌리지 못했고, 두 실행은 정리 단계 말고도 다릅니다. 노트를 다시 넣었고, 어댑터가 다르며, 둘째 실행은 리랭킹 후보 상한이 60입니다. 두 값의 차이를 정리 단계의 효과로 읽을 수 없고, 아래 결론은 이 값에 기대지 않습니다.

## 기준 시스템

베이스라인은 우리가 쓰던 한국어 BM25 검색입니다. 사실마다 출처 줄을 따로 두었고, 아래는 실험에 쓴 판을 기준으로 적었습니다.

- 노트 형식: 마크다운 파일이고 맨 앞에 YAML 머리말이 있습니다. 색인할 때 머리말은 떼고 본문만 씁니다.
- 규모와 언어: 표본은 노트 287개이고 실제 저장소는 약 1,800개입니다. 노트에는 한국어와 영어가 섞여 있고, 언어별 비율은 재지 않았습니다.
- 색인 대상: 노트 본문을 빈 줄에서 잘라 600자 안팎의 조각으로 만들고, 조각마다 맨 앞에 노트 제목을 붙입니다. 한 문단이 1,200자를 넘으면 억지로 자릅니다.
- 형태소 처리: lindera와 ko-dic 사전으로 한국어를 형태소로 나누고 품사 이름표의 첫 글자가 N, V, M, S인 것만 남겨 소문자로 바꿉니다. mecab-ko crate 문서에 적힌 mecab-ko-dic 품사표에서 N은 명사, 대명사, 수사이고, V는 동사, 형용사, 보조 용언, 지정사이며, M은 관형사와 부사이고, S는 문장 부호와 기호, 외국어, 한자, 숫자입니다. 조사, 어미, 접사, 어근, 감탄사는 버립니다.
- 점수: bm25s의 기본 값인 k1과 b로 BM25 점수를 매기고, 노트의 점수는 가장 높은 조각의 점수입니다. 점수가 높은 노트 순서대로 돌려줍니다.
- 답을 쓰는 고정 단계: 상위 5개 노트를 노트마다 앞 6,000자만 잘라 언어 모델에 주고 한두 문장으로 답하게 합니다. 노트에 답이 없으면 "근거 없음"이라고 답하게 합니다.
- 고른 구성: 이 베이스라인 위에 에이전트 검색을 얹은 구성입니다. Hit@5는 100개 중 99였고 answer score는 189(베이스라인은 150)였습니다.
- 참고 행: 결과표의 basic-memory 운영 설정 행은 "우리가 쓰던 의미 검색 설정"입니다. basic-memory 0.23.2의 하이브리드 검색이고, 전문 검색과 벡터를 섞으며, 유사도 임계값은 0.55이며, Hit@5는 100개 중 48이었습니다.
- 비슷한 두 행의 차이: Basic Memory 1.0 제품 행(46)은 제품이 권하는 구성에서 임베딩을 바꾸고 최소 유사도를 0.3으로 낮춰 돌린 값이고, 참고 행(48)은 우리가 운영에서 쓰던 basic-memory 0.23.2 설정(유사도 임계값 0.55)을 쓰던 그대로 잰 값입니다.

동봉한 `baseline/search.py`는 이 베이스라인을 독립된 코드로 옮긴 것입니다. 시연 표본에서 운영 코드와 상위 5개 목록이 같습니다.

## 용어 풀이

- **비교한 구성**: 도구 하나와 그 설정을 묶은 것입니다. 표의 한 행이 구성 하나입니다.
- **베이스라인**: 모든 구성을 견주는 기준으로 삼은 한국어 BM25 검색입니다.
- **Hit@5**: 질문의 정답 노트 가운데 하나라도 상위 5개 안에 있으면 그 질문을 적중으로 셉니다. 정답 노트가 여럿인 질문도 그중 하나만 상위 5개 안에 있으면 적중입니다. 멀티홉 칸은 더 엄격해서, 그 질문의 정답 노트가 모두 상위 5개 안에 있어야 셉니다.
- **승, 패(베이스라인 대비)**: 같은 질문에서 베이스라인은 놓쳤는데 이 구성이 적중한 질문이 승, 베이스라인은 적중했는데 이 구성이 놓친 질문이 패입니다.
- **p값**: 두 구성이 실제로는 같은 수준이라고 해도 승과 패가 이만큼 갈릴 확률입니다. 정확 양측 부호 검정으로 세고, 0.05보다 작으면 차이가 확인된 것으로 읽습니다.
- **부호 검정**: 두 구성이 갈린 질문만 보고, 승과 패가 이렇게 나뉘는 일이 우연히 얼마나 일어날 만한지 셉니다.
- **멀티홉 질문**: 노트 한 개만 읽어서는 답이 나오지 않는 질문입니다. 여기서는 답에 노트 두 개가 필요한 질문 25개이고, 노트 두 개가 모두 상위 5개 안에 있어야 적중으로 셉니다.
- **지식 갱신 질문**: 같은 사실이 나중 노트에서 바뀌었을 때 바뀐 값을 묻는 질문입니다. 유형 이름은 LongMemEval 벤치마크의 질문 유형 이름을 빌렸고, 이 시험의 질문은 그 벤치마크에서 온 것이 아니라 우리 노트에서 만들었습니다.
- **answer score(답 점수)**: 찾은 노트를 읽고 고정된 모델이 쓴 답을 질문마다 0점, 1점, 2점으로 채점해 100개를 더한 값입니다(200점 만점).
- **답을 쓰는 고정 단계**: 찾은 노트를 읽고 답을 쓰는 단계입니다. 모든 구성이 같은 모델과 같은 지시문을 씁니다.
- **실행 점검**: 구성이 권장 구성대로 끝까지 돌았는지 따로 살펴본 절차입니다.
- **권장 구성 실행**: 도구 설명서가 권하는 설정으로 돌린 실행입니다.
- **천장 효과**: 점수가 만점 가까이 모여서 구성 사이의 차이를 가릴 수 없는 상태입니다.
- **모델을 질문당 한 번만 부르는 검색**: 질문마다 모델을 딱 한 번 불러 후보를 고르게 하는 검색입니다.
- **모델에게 노트 목록을 주고 고르게 하는 방법**: 노트마다 한 줄씩 적은 목록을 모델에게 보여 주고 열 노트를 고르게 합니다.
- **기억을 묶어 정리하는 단계**: 기억 저장 제품이 쌓아 둔 기억 조각을 묶어 요약하는 단계입니다.
- **돌리지 않고 결과를 예상해 닫음**: 같은 계열의 값으로 결과를 미리 어림해 시험 없이 닫은 구성입니다.
- **잴 수 없었음**: 조건이 없거나 이 질문으로는 잴 수 없는 종류라서 점수를 내지 못한 구성입니다.
- **보류 중**: 권장 구성을 끝까지 돌리지 못해 중간 결과만 있는 행입니다. 중간 결과라고 표시합니다.
- **중간 결과**: 권장 구성을 끝까지 돌리기 전에 잰 값입니다. 어떤 결론도 이 값에 기대지 않습니다.

[^agent]: **에이전트 검색**: 모델이 검색 도구를 써 가며 단계적으로 노트를 찾는 방식입니다. 파일 찾기 명령을 직접 돌려 노트를 찾아 읽습니다.
[^rerank]: **리랭킹**: 먼저 뽑은 짧은 후보 목록을 두 번째 모델로 다시 줄 세우는 일입니다.
[^embedding]: **임베딩**: 글의 뜻을 숫자 목록(벡터)으로 바꾼 것입니다. 이것으로 낱말이 아니라 뜻이 가까운 노트를 찾습니다.
[^bm25]: **BM25**: 질문과 노트의 낱말이 얼마나 겹치는지로 노트의 순위를 매기는 표준 공식입니다.
[^hit5]: **Hit@5**: 질문의 정답 노트 가운데 하나라도 상위 5개 안에 있으면 그 질문을 적중으로 셉니다. 정답 노트가 여럿인 질문도 그중 하나만 상위 5개 안에 있으면 적중입니다. 멀티홉 칸은 더 엄격해서, 그 질문의 정답 노트가 모두 상위 5개 안에 있어야 셉니다.
[^baseline]: **베이스라인**: 모든 구성을 견주는 기준으로 삼은 한국어 BM25 검색입니다.
[^sign]: **부호 검정**: 두 구성이 갈린 질문만 보고, 한쪽이 이긴 수와 진 수가 우연히 나올 만한지를 셉니다(정확 검정, 양측).
[^p]: **p값**: 두 구성이 실제로는 같은 수준이라고 해도 승과 패가 이만큼 갈릴 확률입니다. 정확 양측 부호 검정으로 셉니다. 0.05보다 작으면 차이가 확인된 것으로 읽습니다.
[^multihop]: **멀티홉 질문**: 노트 한 개만 읽어서는 답이 나오지 않는 질문입니다. 여기서는 답에 노트 두 개가 필요한 질문 25개입니다.
[^update]: **지식 갱신 질문**: 나중 노트가 바꾼 값을 묻는 질문입니다. 유형 이름은 LongMemEval의 질문 유형에서 빌렸고, 이 시험의 질문은 그 벤치마크에서 온 것이 아닙니다.

## 재현과 내 시스템 시험하기

### 시연 표본으로 돌려 보기

시연 표본(노트 12개, 질문 10개)과 표준 라이브러리만 쓰는 측정 도구입니다. Python 3.11 이상이면 됩니다.

```
python harness/run_demo.py --notes demo/notes --questions demo/questions.jsonl --out out
```

`out/top5.jsonl`과 `out/pair-stats.tsv`가 생깁니다. 한국어 형태소 베이스라인은 따로 설치해 돌립니다.

```
pip install -r baseline/requirements.txt
python baseline/search.py --notes demo/notes --cache cache --questions demo/questions.jsonl --k 5 --dict <ko-dic 폴더>
```

### 내 시스템 시험하기

1. 내 노트 폴더와 질문 파일(`spec/question-format.md`)을 만듭니다.
2. 도구 하나를 `adapters/README.md`의 약속대로 붙입니다. 질문 하나를 받아 상위 5개 노트 파일 이름을 돌려주는 명령이면 됩니다.
3. `top5.jsonl`을 모아 `harness/pair_stats.py`에 `--base <베이스라인의 config 이름>`을 주어 베이스라인과 짝 비교를 냅니다. `baseline/search.py`가 같은 줄 모양으로 쓰므로 그 출력도 입력으로 쓸 수 있습니다.
4. answer score가 필요하면 `harness/blind_grade.py`로 구성 이름을 가린 채점 입력을 만들고 `spec/rubric.md`로 채점합니다.

표를 고치려면 `results/results.csv`를 고친 뒤 `python tools/make_tables.py`를 돌립니다. 숫자의 뜻은 이 저장소의 이슈에 한 줄씩 물을 수 있습니다.
